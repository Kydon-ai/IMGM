# Windows 安装器与便携包打包方案复盘

## 一、问题现象

执行项目打包命令后，看到的是：

```text
out\IMGM-win32-x64
```

这个目录可以直接运行应用，看起来像一个“一站式便携包”。用户希望得到的则是一个真正的 Windows 安装器：

1. 用户双击安装器；
2. 安装器显示安装向导；
3. 用户可以自主选择安装目录；
4. 安装完成后创建开始菜单和桌面快捷方式。

## 二、原有打包方式分析

### 1. `electron-forge package` 只生成应用目录

项目原来的 `package` 命令是：

```json
"package": "npm run build && electron-forge package"
```

Forge 的 `package` 阶段主要负责将 Electron 应用整理成可运行目录，因此会生成：

```text
out\IMGM-win32-x64
```

它不是安装器，不负责安装路径选择、快捷方式创建或卸载注册。

### 2. Squirrel 安装器不提供目录选择

项目原来使用：

```js
{
  name: '@electron-forge/maker-squirrel',
  config: {
    setupExe: 'IMGM-Setup.exe',
  },
}
```

Squirrel 确实可以生成 `Setup.exe`，但它的设计目标是无提示、无管理员权限的用户级安装，默认安装到：

```text
%LocalAppData%\IMGM_app
```

因此，修改 `setupExe` 只能修改安装器文件名，不能让 Squirrel 出现安装目录选择页面。

官方文档说明了 Squirrel 使用用户本地应用数据目录作为安装位置：

<https://github.com/Squirrel/Squirrel.Windows/blob/develop/docs/using/install-process.md>

## 三、最终方案

使用 `electron-builder` 的 NSIS 目标生成传统的 Windows 安装向导。

### 1. 新增构建依赖

在开发依赖中加入：

```json
"electron-builder": "^26.15.3",
"tslib": "^2.8.1"
```

其中 `tslib` 是 electron-builder 的代码签名相关依赖。首次安装 builder 时，锁文件中虽然存在 `tslib`，但本地 `node_modules` 没有实际落地，因此通过下面的命令完整恢复依赖：

```powershell
npm ci --include=dev --include=optional --no-audit --no-fund
```

### 2. 新增 `electron-builder.yml`

核心配置如下：

```yaml
appId: tech.qidong.imgm
productName: IMGM
artifactName: IMGM-Setup.${ext}

directories:
  output: out/installer

win:
  icon: public/img/IMGM.png
  target:
    - target: nsis
      arch:
        - x64

nsis:
  oneClick: false
  allowToChangeInstallationDirectory: true
  perMachine: false
  createDesktopShortcut: true
  createStartMenuShortcut: true
  shortcutName: IMGM
```

关键配置的作用：

| 配置 | 作用 |
| --- | --- |
| `target: nsis` | 生成 NSIS Windows 安装器 |
| `oneClick: false` | 使用完整安装向导，而不是一键安装 |
| `allowToChangeInstallationDirectory: true` | 显示安装目录选择页面 |
| `perMachine: false` | 默认使用用户级安装，不强制管理员权限 |
| `artifactName` | 输出固定名称 `IMGM-Setup.exe` |

NSIS 官方配置文档：

<https://www.electron.build/nsis/>

### 3. 保留 Forge 的其他用途

`package.json` 中的命令调整为：

```json
"package": "npm run build && electron-forge package",
"make": "npm run build && electron-builder --win nsis",
"make:forge": "npm run build && electron-forge make"
```

现在：

- `npm run package`：生成可运行的便携应用目录；
- `npm run make`：生成带目录选择页面的 NSIS 安装器；
- `npm run make:forge`：保留旧的 Forge/Squirrel 打包方式，便于兼容旧流程。

## 四、构建过程中遇到的附加问题

### 1. 原有 ICO 尺寸过小

第一次使用 electron-builder 时，发现：

```text
Icon must be at least 256x256 pixels, provided: 32x32
```

原来的：

```text
public\img\IMGM.ico  32x32
```

而项目已有的 PNG 图标尺寸为：

```text
public\img\IMGM.png  1278x1230
```

因此 NSIS 配置改为使用：

```yaml
win:
  icon: public/img/IMGM.png
```

Forge 原来的 ICO 配置仍然保留，不影响旧 Forge 打包流程。

### 2. 防止开发依赖被全部打入安装包

最初在 `files` 中加入了：

```yaml
- node_modules/**/*
```

这会把整个 `node_modules` 目录显式加入应用，容易把开发依赖也带入最终产物。

后续删除这条规则，只保留应用源码、编译产物、页面和静态资源：

```yaml
files:
  - dist/**/*
  - index.html
  - public/**/*
  - package.json
```

electron-builder 会根据 `package.json` 自动收集生产依赖，避免手动全量复制依赖目录。

### 3. 保留原生模块的解包规则

由于项目使用 `sharp` 和 `better-sqlite3`，NSIS 配置中保留：

```yaml
asarUnpack:
  - node_modules/sharp/**/*
  - node_modules/@img/**/*
  - node_modules/better-sqlite3/**/*
```

其中 `@img` 中包含 sharp 在 Windows 上依赖的 libvips DLL。只解包 `.node` 而不解包 DLL，会导致安装后的应用再次出现：

```text
ERR_DLOPEN_FAILED: The specified module could not be found.
```

这与之前的 sharp 打包问题是同一个原生依赖加载链路问题，详见：

`review/4.sharp 原生模块与 Electron 安装包加载失败问题复盘.md`

## 五、最终验证

执行：

```powershell
npm run make
npm test
```

验证结果：

```text
electron-builder 26.15.3
target=nsis
oneClick=false
perMachine=false
```

测试结果：

```text
15 tests passed
0 failed
```

最终安装器：

```text
out\installer\IMGM-Setup.exe
```

同时确认安装器内部的应用目录包含：

```text
sharp-win32-x64.node
libvips-42.dll
libvips-cpp-8.17.3.dll
better_sqlite3.node
```

## 六、使用注意事项

1. `out\IMGM-win32-x64` 仍然是便携应用目录，不是安装器。
2. 用户应该分发 `out\installer\IMGM-Setup.exe`。
3. 当前应用版本仍为 `2.0.0`。测试新安装器时，建议先退出并卸载旧版本，避免同版本安装被旧的 Squirrel 安装记录干扰。
4. 用户选择 `Program Files` 等受保护目录时，Windows 可能要求管理员权限；选择普通用户有写权限的目录则不需要管理员权限。
