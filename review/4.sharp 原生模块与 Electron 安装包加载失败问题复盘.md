# sharp 原生模块与 Electron 安装包加载失败问题复盘

## 一、问题现象

安装 `IMGM-Setup.exe` 后，启动应用立即弹出 Electron 主进程错误：

```text
A JavaScript error occurred in the main process

Error: Could not load the "sharp" module using the win32-x64 runtime
ERR_DLOPEN_FAILED: The specified module could not be found.
```

错误堆栈指向安装目录中的：

```text
resources\app.asar\node_modules\sharp\...
```

由于 `src/main.ts` 在主进程中直接引入 `sharp`，所以 `sharp` 加载失败会阻止整个应用启动，而不是只影响某一个图片处理功能。

## 二、排查过程

### 1. 确认依赖和平台

项目使用：

```text
Electron 33.0.2
Windows x64
sharp 0.34.5
@img/sharp-win32-x64 0.34.5
```

本地 Node.js 环境可以正常执行：

```text
sharp 8.17.3
```

说明 `sharp` 依赖本身已经安装，问题集中在 Electron 打包后的文件布局和原生库加载路径。

### 2. 检查原安装包的文件布局

原来的 Forge 配置为：

```js
packagerConfig: {
  asar: true,
}
```

项目同时启用了 `@electron-forge/plugin-auto-unpack-natives`。该插件默认使用类似下面的规则：

```text
**/{.**,**}/**/*.node
```

也就是说，它会自动解包原生 `.node` 文件，但不会自动解包 `sharp` 运行时依赖的 DLL。

原安装包的实际情况是：

```text
app.asar.unpacked\node_modules\@img\sharp-win32-x64\lib\sharp-win32-x64.node
```

存在，但：

```text
app.asar.unpacked\node_modules\@img\sharp-win32-x64\lib\libvips-42.dll
app.asar.unpacked\node_modules\@img\sharp-win32-x64\lib\libvips-cpp-8.17.3.dll
```

不存在。两个 DLL 仍然被放在 `app.asar` 内。

### 3. 复现底层错误

直接加载原安装包中已经解包的 `.node` 文件，得到相同错误：

```text
Error: The specified module could not be found.
```

这里的“模块不存在”并不表示 `.node` 文件本身不存在，而是 Windows 加载 `.node` 时找不到它依赖的 DLL。DLL 位于 asar 虚拟文件系统中，不能作为普通 Windows 文件被原生加载器解析。

## 三、根本原因

`sharp` 在 Windows 上不是只有一个 `.node` 文件，还依赖同目录下的 libvips 动态库：

```text
sharp-win32-x64.node
libvips-42.dll
libvips-cpp-8.17.3.dll
```

原配置只解包了 `.node`，没有解包 `@img` 目录的完整内容，最终导致：

```text
JavaScript 模块在 app.asar 中可见
原生 .node 被放到了 app.asar.unpacked
Windows 原生加载器找不到同目录 DLL
sharp 加载失败
主进程启动失败
```

这不是图片文件问题，也不是 `sharp` 版本与 Windows x64 不兼容。

## 四、解决方案

在 `forge.config.js` 中把 `sharp` 和 `@img` 的完整目录解包：

```js
packagerConfig: {
  asar: {
    unpack: '**/node_modules/{sharp,@img}/**/*',
  },
}
```

保留 `@electron-forge/plugin-auto-unpack-natives`，让它继续处理其他原生 Node 模块；手动规则负责补充 `sharp` 所需的 DLL 和相关运行时文件。

这是 sharp 官方针对 Electron Forge 给出的配置方式：

<https://sharp.pixelplumbing.com/install/#electron>

## 五、修复后的验证

修复后重新执行：

```powershell
npm run package
npm run make
```

两条命令均成功完成。

新的 `app.asar.unpacked` 中同时存在：

```text
node_modules\@img\sharp-win32-x64\lib\sharp-win32-x64.node
node_modules\@img\sharp-win32-x64\lib\libvips-42.dll
node_modules\@img\sharp-win32-x64\lib\libvips-cpp-8.17.3.dll
```

直接加载新的原生模块验证成功：

```text
native addon ok object
```

新的安装器已经生成：

```text
out\make\squirrel.windows\x64\IMGM-Setup.exe
```

对应的 Squirrel 包中也确认包含上述 DLL 文件。

## 七、后续注意事项

1. 修改 Electron 打包配置后，不能只检查 `.node` 文件，还要检查原生模块依赖的 DLL 是否也位于 `app.asar.unpacked`。
2. 使用新的安装器测试时，应先退出旧版 IMGM。当前应用版本仍为 `2.0.0`，为避免 Squirrel 将相同版本识别为已安装版本，建议先卸载旧版本再重新安装。
3. `npm warn deprecated boolean@3.2.0` 与本次启动崩溃无直接关系；它只是依赖树中的弃用警告。`npm warn cleanup ... EPERM` 也属于 Windows 文件被占用时的清理警告，不是本次 `sharp` 加载失败的根因。
