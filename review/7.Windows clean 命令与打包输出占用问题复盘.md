# Windows clean 命令与打包输出占用问题复盘

## 一、问题现象

Windows 上一次 Electron Builder 打包失败后，再执行：

```powershell
npm run clean out
```

删除输出目录时报错：

```text
EBUSY: resource busy or locked, unlink
...
out\installer\win-unpacked.tmp\resources\default_app.asar
```

Windows 不允许删除仍被进程句柄占用的文件。`EBUSY` 能说明文件当前无法删除，但不能单凭报错确认是哪一个进程持有句柄。打包失败后残留的构建进程、正在读取产物的程序或系统扫描都可能造成短暂占用，因此不能假定每次都是 Electron Builder 自身，也不能靠 `rimraf` 保证强制释放句柄。

## 二、处理思路的调整

最初考虑过使用 Windows Restart Manager 关闭占用输出目录的进程，以便继续删除。这个方案会关闭整个应用，而不是只释放某个文件句柄；用户反馈 VS Code 受到影响后，方案调整为只检查并显示占用进程，不再关闭或终止任何进程。

直接结束未知进程会带来比构建失败更大的影响。若需要人工确认具体占用者，可查看 `[inspect-output-locks.ps1](../scripts/inspect-output-locks.ps1)` 的扫描结果，再自行决定是否关闭对应程序。

## 三、最终处理方案

### 1. `clean` 只删除白名单目录

清理目标限制为项目根目录下的 `dist`、`out`、`data` 和 `node_modules`，拒绝绝对路径及多级路径，避免把任意路径传给递归删除工具。

```powershell
# 默认清理 out 和 dist
npm run clean

# 指定一个白名单目录
npm run clean -- out
npm run clean -- dist
npm run clean -- node_modules
npm run clean -- data
```

手动指定 `data` 会删除整个数据目录，包括应用数据库和已下载的模型；不带参数运行 `npm run clean` 仍只清理 `out` 和 `dist`。

清理按顺序执行。若某个目录因占用而删除失败，会记录失败并继续尝试后面的目录，命令最终仍以非零状态报告失败。对 `out` 执行清理前会检查并报告占用情况；检查不会关闭占用进程。`rimraf` 配置了有限重试，但如果句柄持续被占用，删除仍会失败。

### 2. Windows 一键打包自动切换输出目录

本地 Windows 打包使用：

```powershell
npm run make:win
```

该命令先构建应用，再由 `[build-windows.cjs](../scripts/build-windows.cjs)` 检查并尝试清理默认目录 `out/installer`：

- 默认目录可删除：生成 Windows NSIS 安装器和 ZIP 到 `out/installer`；
- 默认目录持续被占用：保留原目录，改用 `out/installer-retry-时间戳-进程号` 打包。

electron-builder 使用 `--publish never`，本地打包不会发布。直接执行 `npx --no-install electron-builder ...` 会绕过这个备用目录逻辑；遇到旧产物占用时，应使用 `npm run make:win`。

### 3. CI 中只检查，不强制释放

GitHub Release workflow 在 Windows 构建前调用 `node scripts/inspect-output-locks.cjs out/installer`，随后按 workflow 中的参数运行 electron-builder。检查步骤只报告进程，不会关闭它们。CI 使用新的 runner 工作目录，和本地多次打包留下旧输出的情况不同；CI 当前仍写入固定的 `out/installer`，没有本地脚本里的备用目录切换逻辑。

## 四、验证与边界

- `scripts/clean.cjs` 通过 Node.js 语法检查。
- 使用不在白名单内的路径验证了清理命令会拒绝该输入。
- 对 `out` 和 `dist` 的真实删除未作为验证步骤执行，以免清除项目现有构建产物。
- 这套方案避免因清理失败而结束用户程序；它不承诺在句柄仍被占用时强行删除原目录。需要稳定完成本地打包时，`make:win` 的备用输出目录是自动恢复路径。
